# TakMD 한강뷰 제작 계획

2026-09-09 · 기준 배포 `20ff4725621e180de9d302619944feee1a58aa70`

> 진행 업데이트: 반포 GLB revision 3을 실제 방에서 확인한 뒤 사용자가 2026-09-09 “여기까지라도 커밋 푸시 배포”를 승인했다. 기본 화면에서 다리가 보이도록 고정 관찰 지점을 조정하고 반포를 기본 장면으로 적용했다. 건물·녹지의 사실감과 실기기 성능은 다음 작업이며, 이 중간 배포는 아래 최종 품질 기준을 달성했다는 뜻이 아니다. 현재 현황은 `docs/han-river-pilot-status-2026-09-09.md`, 배포 근거는 `.omo/evidence/banpo-release-2026-09-09/release.json`을 따른다. 아래 본문은 제작 전 조사 기록이다.

목표는 창가로 다가가거나 좌우로 움직여도 형태와 깊이가 유지되는 한강뷰다. 방과 어울리는 낮의 재질, 저녁의 공기감, 밤의 교량 조명과 수면 반사가 필요하다. 기존 방·가구·조작법은 유지한다. 이번 산출물은 조사에 근거한 제작 계획이며 새 한강 장면 생성은 아직 시작하지 않았다.

## 2. 지금 사용할 수 있는 Higgsfield 기능

[공식 3D Jutsu 안내](https://higgsfield.ai/blog/higgsfield-3d-jutsu)를 브라우저에서 읽었다. 프롬프트·참고 자료로 편집 가능한 장면을 만들고, 카메라·조명·배치를 수정하며 GLB 또는 이미지·영상으로 내보내는 기능이 있다. 공식 문서는 3D 배치/사전 시각화와 이를 바탕으로 한 영상 제작을 구분한다.

현재 연결된 플러그인의 도구 계약도 확인했다.

- 3D 프로젝트 생성·조회, Blender Python으로 장면 편집 및 렌더 검토가 가능하다.
- 제공 카탈로그에서 GLB를 검색·가져오는 도구, 최종 GLB와 편집 가능한 `.blend`를 받는 도구가 있다.
- Meshy/Tripo의 이미지 기반 GLB·PBR 생성 도구도 있다. 개별 자산 후보를 만드는 데 사용할 수 있지만 한강 전체의 정확한 지리를 자동 복원한다고 가정하지 않는다.
- 3D Jutsu 카탈로그 검색은 프로젝트 ID가 필요하다. 현재 계정의 프로젝트 목록은 비어 있다. 이번에는 새 프로젝트나 생성 작업을 제출하지 않았으며, 사용할 완성 한강 자산을 확보했다고 주장하지 않는다.
- GLB는 Blender의 절차적 셰이더·월드 조명·후처리를 그대로 보장하지 않는다. 표준 PBR 재질과 텍스처를 사용하고, 웹에서 쓸 조명과 수면은 별도로 검증한다.

제작 시에는 사진·영상 예시의 분위기를 목표로 삼되, 최종 납품의 기준은 Three.js에서 확인한 장면으로 한다. 영상 생성은 나중에 소개 영상이나 선택형 창밖 투어를 만들 때 활용할 수 있다.

## 4. 권장 구도와 제작 순서

### 단계 A. 실제 구도와 자산 후보 확정

2026-09-09 사용자가 제공한 사진 10장을 반영해, 기존 여의도 우선안 대신 **반포 남측에서 반포대교·세빛섬 너머 북측 강변과 남산을 바라보는 구도**를 시범의 우선안으로 제안한다. 아직 새 외부 장면 생성은 시작하지 않았다.

- 주 구도·지리: 사진 4~8의 같은 강변/다리 계열. 사진 6·7을 구조 기준으로 삼고 4·5를 야간 조명의 참고로 쓴다. 세빛섬이 반포대교 남단 하류에 있다는 [서울시 설명](https://hangang.seoul.go.kr/www/contents/804.do?mid=528)과 [서울연구데이터서비스의 반포대교·남산 기록](https://data.si.re.kr/node/47294)으로 위치 관계를 교차 확인했다. 정확한 카메라 위치와 각도는 지도와 일치시킨 뒤 확정한다.
- 공간감·색: 사진 2처럼 넓은 수면과 강변 녹지가 먼저 보이고, 건물은 강 건너 중·원경으로 배치한다. 3번의 저녁 수면/도로 빛은 분위기 참고로만 사용한다. 1~3번의 정확한 촬영 지점은 미확인 상태이며 그 건물과 다리를 반포 장면에 임의 합성하지 않는다.
- 시점: 기존 외부 카메라의 340m 높이를 그대로 쓰지 않는다. 40~80m의 중고층 시점에서 시범 구도를 비교해 창밖으로 넓은 물과 교량이 함께 보이는 높이를 고른다. 사진 10의 항공 촬영 높이는 깊이감 참고용이다.
- 낮: 2·7번의 맑은 대기, 청회색 물, 녹지, 명확한 명암을 기준으로 삼는다. 실내의 따뜻한 일광과 외부의 자연스러운 하늘빛이 이어져야 한다.
- 해질녘·밤: 6번의 옅은 살구색 하늘에서 3·4번의 푸른 야경으로 이어지게 한다. 5번의 보라색 분수는 상시 기본 조명으로 채택하지 않는다. 교량과 도로는 따뜻한 백색, 수면은 길고 깨지는 반사로 표현한다.
- 하나의 지형과 건물 배치로 낮·저녁·밤을 만든다. 사진은 재질/구조/구도를 읽는 참고이며 평면 배경으로 붙이지 않는다.

원본과 이미지별 역할은 [참고 보드](reference-assets/han-river-2026-09-09/README.md)에 보존했다. 공개 출처의 사용 조건과 자산별 내보내기 가능 여부를 확인한 다음 3D Jutsu 시범을 진행한다. 워터마크가 있는 9·10번은 시각 검토 자료로 유지한다.

산출물:

1. 같은 시점의 지도 방향, 대표 낮/밤 사진, 교량 측면·교각 자료를 담은 참고 보드.
2. 실내 창문 카메라에 맞춘 정면·좌측·우측 구도 3개. 강이 주역이며 아파트 벽이 창을 막지 않아야 한다.
3. 자산 목록: 저자/출처/사용 조건/다운로드 확인/삼각형 수/텍스처/수정 필요 부분.

자산은 3D Jutsu 카탈로그와 전문 제작자의 내려받을 수 있는 모델부터 조사한다. 기존 기록의 [river han 후보](https://sketchfab.com/3d-models/river-han-8e454ca416af4b5cbbe5c774dfc49ddd)는 이번에도 실제 다운로드 패키지를 확인하지 못했으므로 선정 자산으로 취급하지 않는다. 검색되는 일반 서울 거리 모델도 창밖 한강 전경을 충족하는지는 별도 판정한다. 사용 조건이 AI 입력을 제한하는 자료는 Higgsfield에 업로드하지 않는다.

### 단계 B. 한 구간을 완성하는 시범 제작

Higgsfield 3D Jutsu에 별도 한강 프로젝트를 만들고, **주 교량 하나 + 연결되는 양쪽 강변 + 주요 건물군**만 작업한다. 확보한 모델을 우선 사용하며 부족한 구조만 참고 자료에 따라 보완한다.

- 교량을 도로/난간/거더/교각/받침/등기구로 구분한다. 교량 끝은 강변 도로에 실제로 연결한다.
- 건물은 거리별 높이·층 밀도·옥상 윤곽·재질이 구별되게 한다. 균일한 상자 배열을 다시 만드는 것은 시범 합격으로 보지 않는다.
- 콘크리트 거칠기, 유리 반사, 창문 발광은 각각 조절 가능하게 한다. 빛이나 반사를 표면 사진에 통째로 굳히지 않는다.
- 낮/해질녘/밤을 같은 기하에서 만든다. 세 장의 별개 생성 결과를 겹쳐 건물 위치가 달라지는 방식은 사용하지 않는다.
- 사진 속 야경의 조명 위치와 수면의 길게 깨지는 반사를 참고하되, 낮에도 회색 덩어리로 보이지 않아야 한다.

시범 산출물은 `.blend`, 웹용 `.glb`, 텍스처, 출처 기록, 동일 카메라의 낮·밤 렌더다. 최종 재질을 포함한 GLB를 Three.js로 다시 열어 검토한 결과도 남긴다. 생성된 영상의 품질로 시범 GLB 검사를 대신하지 않는다.

### 단계 C. 실제 방에 넣어 비교

`HanRiverLandscape.ts`의 장면 생성 함수가 교체 지점이다. 기존 `scene / setNightMix / setTime / dispose` 연결을 유지하며 GLB 로더를 붙인다. 비동기 로딩 중 빈 창이 생기지 않도록 완성된 그룹을 준비한 뒤 교체하고, 실패하면 현재 장면을 유지한다. 언마운트 시 뒤늦게 도착한 결과와 새 텍스처도 정리한다.

- `WindowSky.tsx`: 기존 창문 포털·실내 카메라 연결을 유지하면서 검증한 외부 기준 높이/방향을 적용한다.
- `HanRiverLandscape.ts`: 새 지형·건물·교량 자산을 넣고 낮·밤 재질 및 자원 정리 함수를 연결한다.
- `HanRiverTraffic.ts`: 기존 차량 인스턴스를 새 도로의 차선·경사·양 끝에 맞춘다.
- `HanRiverAtmosphere.ts`: 실제 반사 결과를 보고 수면 색·노멀·반사 선명도를 조절한다. 반사 텍스처 확대는 프레임 시간 측정 후 선택한다.
- 필요 시 `HanRiverAssets.ts`, `public/models/han-river/`, 자산 준비 스크립트를 추가한다. 기존 방 모델이나 연구 콘텐츠는 건드리지 않는다.

Blender 조명과 GLB 표준 재질의 차이를 보정한다. 일광의 방향성 그림자를 텍스처에 굳혀 밤에 남기지 말고, 필요한 경우 제한된 범위의 외부 그림자나 전환 가능한 베이크를 별도 검증한다. 화면 전반의 과노출이나 중복 색 변환 여부도 테스트한다.

### 단계 D. 시범 통과 후 넓히기

측면 원경의 두 번째 실제 다리, 추가 강변 건물군, 먼 산과 도시의 층을 순서대로 확장한다. 가까운 요소는 입체 구조를 유지하고 멀리 있는 요소는 단순화·묶음 렌더를 사용한다. 차량·수면의 움직임은 잔잔하게 유지한다.

불꽃축제는 기본 야경이 완성된 후 별도 이벤트로 추가한다. 실제 개최일과 시간을 확인한 설정으로 다루며 지금 미확인 일정에 자동 연결하지 않는다. 실내 탐색 중 자동 드론 이동이나 카메라 흔들림은 추가하지 않는다.

## 5. 시범 합격 기준

| 점검 | 통과 기준 |
| --- | --- |
| 화면 비교 | 현재 버전과 새 버전을 같은 카메라·시간·노출로 나란히 비교한다. 다리 구조와 강변 건물의 차이가 명확해야 한다. |
| 근접/좌우 보기 | 기본 방 구도, 창가 근접, 좌측/우측 최대 탐색을 확인한다. 평면 옆면 노출, 지평선 점프, 다리·강변 절단, 물체 겹침이 없어야 한다. |
| 낮·밤 | 낮에도 재질과 입체가 읽힌다. 밤에는 교량·도시 조명만 적절히 발광하며 낮 그림자가 남지 않는다. 같은 건물의 위치와 형태가 유지된다. |
| 수면 | 교각 접점·수면·반사 방향이 맞는다. 다리 아래 반사가 화면 중간에서 사각형으로 끊기거나 길쭉한 검정 판처럼 보이지 않는다. |
| 움직임 | 차량은 도로 높이에 있고 다리 끝에서 갑자기 출몰하지 않는다. reduced motion에서 연속 움직임은 멈춘다. |
| 성능 | MacBook Air 일반 브라우저와 모바일에서 현재 버전 대비 프레임 시간을 기록한다. 목표는 데스크톱 50–60fps, 모바일 30fps 이상이며 기기별 실측으로 판정한다. 아직 달성했다고 주장하지 않는다. |
| 초기 자산 예산 | 시범 GLB와 텍스처 합계 8MB 이하, 삼각형 25만 이하, 추가 draw call 60개 이하를 출발 목표로 삼는다. 실제 화면/반사 패스 비용을 측정해 조정한다. |
| 회귀 | 두 블라인드·조명 프리셋·사진창·오브젝트 선택·가구 이동이 작동한다. 재진입 후 렌더 타깃·텍스처가 누적되지 않는다. |

## 6. 진행 보고와 완료 정의

보고는 **참고 보드/실제 구도 → 다리·강변 시범 → 방 안 낮·밤 비교 → 전체 확장** 순서다. 각 단계는 볼 수 있는 결과물로 판단한다. 이번처럼 구조적으로 다른 제작 방식을 시작할 때는 완성되지 않은 외부 장면을 즉시 운영 사이트에 덮어쓰지 않는다.

첫 구현 단계의 완료는 한 구간의 GLB를 실제 창문에서 보고, 근접·좌우·낮·밤·성능을 확인한 상태다. 이후 비교 결과를 반영해 전체 한강뷰로 확장한다. 현재까지 생성 비용이나 제작 기간은 확정하지 않았다. 실제 모델/자산 조건을 정한 뒤 표시되는 비용을 확인하며, 계획 조사 단계에서 생성 작업은 제출하지 않았다.
